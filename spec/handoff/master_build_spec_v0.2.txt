0. Instruction to Opus 5
You are the implementation lead. Do not respond with another high-level architecture essay. Use this document as the implementation contract and build the project incrementally.
The project already has a v0.1 seed bundle named spatial_ir_roundtrip_v0_1. If that bundle is supplied, preserve its benchmark contract and evolve it in place. If it is not supplied, recreate the same baseline from the normative details in this document before adding v0.2 functionality.
Your first success condition is not photorealism. It is a complete, measurable loop:
known structured world    -> sensor observations    -> inverse spatial compiler    -> predicted Spatial IR    -> target world    -> simulated observations    -> quantitative comparison
The inverse compiler must never read hidden ground-truth IDs, semantic labels, USD prim paths, or simulator-only metadata in the standard benchmark track.
Do not fake execution results. Every reported metric, benchmark, screenshot, or output path must come from a command that actually ran. If a dependency such as Isaac Sim is unavailable, keep the interface, use a deterministic simulator-independent fallback where possible, and clearly mark the unexecuted NVIDIA-specific step.
Do not collapse the architecture into a mesh generator. Meshes are target representations. Spatial IR is the stable representation of world identity, semantics, topology, evidence, uncertainty, and multiple geometry forms.
Do not make the core NVIDIA-only, CUDA-only, Unreal-only, or browser-only. NVIDIA RTX LiDAR is an important validation backend, not the definition of the project. The core should run with ordinary Python/C++ dependencies and should be portable across CPU, CUDA, and ROCm where practical.

2. Why this architecture, and what is already prior art
Do not claim novelty for individual components that already exist. The literature and product landscape shows strong prior art for nearly every isolated layer:
MIT SPARK Hydra / Spark-DSG: hierarchical dynamic 3D scene graphs from sensor observations; closest precedent for the semantic/topological world-graph layer.
TU Delft City3D / 3D BAG / 3dfier / City4CFD: airborne LiDAR and GIS to structured buildings, LoDs, and simulation-ready city geometry.
OGC CityGML 3.0 / CityJSON: platform-independent semantic information models for urban objects, geometry, hierarchy, relations, and LoDs.
NVIDIA Omniverse / Isaac Sim RTX LiDAR: known USD world to synthetic LiDAR with rich per-return ground truth; ideal forward operator for synthetic supervision and reconstruction closure.
Esri CityEngine / CGA: structured geographic objects to procedural architectural geometry, styles, and textures; strongest precedent for the theme/geometry compiler.
Cesium / 3D Tiles: large-world hierarchical streaming, semantic metadata, engine integration, geospatial coordinate handling.
ETH Point2Building: learned airborne LiDAR to polygonal building reconstruction.
Superpoint Graph / Superpoint Transformer / SuperCluster / EZ-SP: scalable point-cloud partitioning into hierarchical superpoints, semantic segmentation, and graph clustering.
Amsterdam Urban PointCloud Processing: LiDAR + public GIS/elevation/topographic data fusion for automatic urban labeling and region growing.
GSeg3D / Patchwork++ and related systems: ground segmentation.
PDAL / Open3D / PCL / CloudCompare: mature point-cloud processing primitives.
CARLA / AirSim / Gazebo / Isaac Sim: sensor simulation backends.
The project should therefore reuse or adapt mature components and spend research effort on the missing composition:
point / superpoint evidence    -> structural role    -> semantic component    -> object hierarchy    -> relations and topology    -> provenance-aware Spatial IR    -> semantic LOD / materialization    -> forward physical consistency
The strongest differentiators to preserve are:
1.  Observed vs inferred vs generated state is first-class.
2.  Provenance is attached to entities, geometry, and relations rather than being a detached log.
3.  The IR can hold multiple simultaneous geometry representations for one semantic entity.
4.  Semantic resolution is separate from polygon resolution.
5.  The inverse reconstruction can be closed through a forward sensor model.
6.  The same IR can be rematerialized under arbitrary themes without re-running perception.
7.  The project is engine-agnostic and simulator-backend-agnostic.

v0.1 invariants that must not be lost:
The world model is not the mesh.
Entity IDs are stable inside a document.
Entity kind and extensible semantic class are distinct.
Geometry is a list of replaceable representations.
Geometry has roles such as source, analysis, render, collision, proxy, and extent.
epistemic_state distinguishes observed, inferred, generated, manual, imported, and hybrid.
Provenance records identify mode, source/evidence IDs, algorithm/version, parameter hash, timestamps, and notes.
Semantic resolution is categorical (macro, object, part, component, detail) and separate from mesh density.
Relations are first-class directed edges with their own confidence and provenance.
Observations are separate objects; entities point back to them through provenance.
Competing hypotheses may coexist through alternatives.
Simulator-only ground truth is evaluation-only in the standard inverse track.
The existing closure benchmark is:
P = F(S)S_hat = R(P)P_hat = F(C(S_hat))
and evaluates at least:
E_geometry(S, S_hat)E_semantics(S, S_hat)E_topology(S, S_hat)E_provenance(S_hat)D_sensor(P, P_hat)
v0.2 should extend this, not replace it.
4. Definition of done for the first build
A first serious implementation is complete when all of the following are true:
1.  A user can provide a .las or .laz point cloud and optional GIS side inputs.
2.  The pipeline writes a schema-valid predicted.sir.json.
3.  The SIR contains ground/terrain and at least one non-ground object or building component when present in the data.
4.  The SIR records evidence and provenance for every inferred entity.
5.  The system derives multiscale geometric descriptors and at least basic structural roles such as surface interior, boundary, edge/corner candidate, ground junction, and roof junction where evidence supports them.
6.  The system creates object/component hierarchy and graph relations rather than only per-point labels.
7.  The SIR can compile to an inspectable USD scene without changing semantic IDs.
8.  A synthetic benchmark can run end-to-end without using hidden ground truth during reconstruction.
9.  The benchmark reports geometry, semantic, relation/topology, confidence/provenance, and sensor-space metrics separately.
10.  A simple theme can rematerialize at least two semantic classes or structural roles without changing the reconstructed Spatial IR.
11.  The repository contains unit tests, deterministic example data, a one-command smoke test, and a build-status report with actual executed commands.
Photorealism, full-city reconstruction, window-perfect airborne reconstruction, and a production game runtime are not required for this first milestone.

7. Spatial IR v0.2: normative model
v0.2 should remain JSON-serializable and schema-valid. Python dataclasses or Pydantic models may be used internally, but JSON Schema remains the interchange contract.
7.1 World
Required world-level fields:
sir_versionworld.idworld.linear_unit = "m"world.up_axis = "Z"world.coordinate_frameworld.crs (nullable)world.originentities[]relations[]observations[]alternatives[]metadata
For geospatial data, preserve the original CRS and also support a local metric frame for numerically stable reconstruction/rendering.
7.2 Entity identity and hierarchy
Each entity must include:
idkindclasssemantic_resolutionepistemic_stateconfidencegeometry[]provenance[]attributeslabels
Add explicit hierarchy fields or standardized relations so the following can be represented cleanly:
World  -> Region / Tile    -> Building      -> Roof      -> Wall        -> SurfaceInterior        -> Edge        -> Corner        -> OpeningBoundary      -> Window / Door    -> Road      -> Segment      -> Curb / Boundary    -> Vegetation      -> Tree / Canopy / Trunk hypothesis
Prefer first-class part_of / contains relations over duplicating hierarchy in two unrelated mechanisms. A cached parent field is acceptable for speed if it is validated against relations.
7.3 Structural roles
Add an extensible structural_roles field. This is the direct formalization of the original "edge dots versus center-mass dots" idea.
Minimum generic role vocabulary:
surface_interiorsurface_boundarylinear_edgeconvex_edgeconcave_edgecorneropening_boundaryground_junctionroof_junctionobject_contactridgevalleyeavecurb_edgeroad_center_regionocclusion_boundaryunknown_structural_role
Structural role is not the same as semantic class.
Example:
{  "class": "WallSurface",  "structural_roles": ["convex_edge", "roof_junction"],  "attributes": {    "orientation": "vertical",    "faces_street": "road_7"  }}
7.4 Multiscale descriptors
Do not store every raw descriptor in the canonical IR by default. Store dense point/superpoint descriptors in analysis sidecars and promote only persistent or useful summaries to the entity.
The geometry engine should compute, where meaningful:
surface normallocal covariance eigenvaluesplanaritylinearityscattering / sphericityroughnesscurvature proxynormal variationverticalityheight above groundpoint densityboundary scoreneighbor-class transitionsdistance to grounddistance to candidate roof/opening/road
Compute at multiple neighborhood scales. Use configurable metric radii and/or k-nearest neighborhoods because sensor densities vary.
For local covariance C with eigenvalues lambda1 >= lambda2 >= lambda3, useful derived quantities include:
linearity  = (lambda1 - lambda2) / lambda1planarity  = (lambda2 - lambda3) / lambda1scattering = lambda3 / lambda1
The eigenvector of the smallest eigenvalue is a local surface-normal estimate when the neighborhood is sufficiently planar.
7.5 Geometry representations
One entity may simultaneously reference:
observed point evidenceanalysis points / superpointssparse occupancy / octreeanalytic plane / primitivepolygon / polylinerender meshcollision proxyprocedural parametersexternal target geometry
Identity remains the same even as representations change.
This is a key invariant:
semantic identity != mesh identity
7.6 Epistemic state and provenance
Keep v0.1 states:
observedinferredgeneratedmanualimportedhybrid
A roof measured directly by LiDAR may have observed point evidence but an inferred fitted plane. Do not incorrectly mark the plane itself as observed.
Example:
Roof_8 source points -> observedRoof_8 fitted plane  -> inferred/geometric_inferenceRoof_8 class label   -> inferred/semantic_inference or imported GIS evidenceVictorian dormer     -> generated/theme grammar
Provenance must be attached independently to geometry, semantics, and relations when their sources differ.
7.7 Confidence and calibration
Keep separate confidence axes:
overallgeometrysemanticstopology
Add optional fields for:
observabilitysupport_strengthcalibration_method
Confidence is not decoration. Evaluate calibration with Brier score and expected calibration error where appropriate.
7.8 Observability: required v0.2 addition
A central problem in airborne LiDAR is that many surfaces are physically unobserved, especially vertical facades and windows. The benchmark must not confuse "not seen" with "failed reconstruction."
Add observation-support records such as:
{  "observation_id": "scan_001",  "point_count": 184,  "visibility_fraction": 0.73,  "mean_range_m": 43.2,  "incidence_angle_deg_p50": 18.5,  "support": "direct_return"}
Possible support states:
direct_returnoccludedout_of_fovbelow_sampling_densityinferred_from_contextimported_externalunknown
All benchmark metrics should be reportable both globally and stratified by observability.
7.9 Relations
Core relation vocabulary:
part_ofcontainsboundsbounded_byadjacent_toconnected_tosupportsintersectsinsidederived_fromcorresponds_toabovebelowfacesoccludesparallel_toperpendicular_to
Each relation has:
idtypesourcetargetconfidenceprovenanceattributes
Relations are not merely derived convenience fields. They are part of the representation being evaluated.
7.10 Alternatives and hypotheses
Preserve multiple candidate interpretations when evidence is ambiguous.
Examples:
roof type: hip 0.58 / gable 0.42wall continuation: candidate A 0.71 / candidate B 0.29opening: real window 0.46 / occlusion gap 0.54
Do not force uncertain airborne data into false precision.
7.11 Time and versioning
Design for time without requiring a full temporal engine in v0.2.
Entities and observations should support:
valid_fromvalid_toobserved_atsupersedessuperseded_by
This allows later evolution from static world reconstruction to temporal world state.
8. Inverse compiler: implementation pipeline
The inverse compiler should be staged and inspectable. Each stage writes diagnostics so failures can be localized.
Stage 1 - Ingest and normalize
Inputs:
LAS / LAZNPZ synthetic observationsoptional GeoJSON / Shapefile / CityJSON / footprint vectorsoptional imagery metadataoptional sensor trajectory/calibration
Required actions:
preserve original CRS and coordinate metadata;
transform to local metric working coordinates;
preserve LAS dimensions such as classification, intensity, return number, GPS time when present;
record preprocessing history and hashes;
tile very large inputs deterministically;
never discard original source observations.
Recommended libraries:
PDAL and/or laspy for LAS/LAZpyproj for CRS transformsGeoPandas/Shapely for vector GISNumPy/SciPy for baseline geometryOpen3D/PCL adapters where useful
Stage 2 - Ground and terrain
Backend choice should depend on modality:
Airborne / public LiDAR:
1.  Use trustworthy existing LAS ground classification as evidence when available.
2.  Otherwise use a suitable airborne ground filter such as a PDAL ground-classification pipeline.
3.  Derive a terrain/DTM representation and height-above-ground feature.
Mobile / terrestrial LiDAR:
Use an adapter for GSeg3D, Patchwork++, or equivalent when available, with a deterministic fallback.
Ground segmentation output must be evidence, not the final world model.
Stage 3 - Multiscale neighborhoods and descriptors
Build scalable neighborhood queries using a KD-tree, voxel hash, sparse grid, octree, or GPU graph depending on scale.
Compute multiscale geometry features. Persist a compact analysis sidecar keyed by stable point/superpoint indices.
Stage 4 - Partition points into coherent regions
Use an interchangeable partition backend.
Required baseline:
deterministic voxel + region-growing or supervoxel partitioner that works without learned weights.
Preferred experimental backend:
EZ-SP / Superpoint Transformer style hierarchical superpoint partitioning.
The adapter should convert backend-specific clusters into a common form:
partition_idmember point indicescentroidbboxnormal summaryfeature summaryneighbor partitionssource observation IDs
Do not let an SPT-specific internal structure become the canonical IR.
Stage 5 - Semantic evidence
Treat semantic segmentation as evidence for graph construction, not the final product.
Sources may include:
ASPRS/LAS classesSPT or another point modelGIS footprintsroad centerlines/polygonsaerial or street imageryheight/shape rulesopen-vocabulary models later
Fuse evidence explicitly and preserve source provenance.
For the deterministic baseline, implement rules that can at least distinguish:
ground/terrainbuilding candidatevegetation candidateroad/transport candidateunknown
Use existing LAS classification as a prior, not unquestioned truth.
Stage 6 - Geometric reconstruction
Start with simple primitives and fitted surfaces before learned mesh generation.
Minimum baseline:
RANSAC or robust plane extraction;
horizontal/vertical orientation classification;
connected surface region growing;
boundary extraction;
plane intersection lines;
roof/wall candidate grouping;
terrain mesh or height-field proxy;
object extents and bounding volumes.
Do not synthesize facade detail during reconstruction benchmark runs.
Later interchangeable backends can include City3D-like methods, Point2Building-like learned reconstruction, or custom parametric methods.
Stage 7 - Structural-role inference
This is a central project-specific layer.
For each patch/surface/component, infer contextual role using geometry and graph neighborhood:
interior vs boundaryedge vs cornerconvex vs concave junctionnear groundnear roofnear openinga street-facing surfacepart of ridge/eave/valleyroad boundary / curb candidate
The role inferencer should use both continuous descriptors and explicit neighborhood relations. A bitmask may be used as a compact local feature, but the canonical representation is not restricted to a voxel mask.
Stage 8 - Object hierarchy
Create stable semantic entities:
points/superpoints -> surface -> component -> object -> region/tile
Example:
Building_17  Roof_1    RoofPlane_1    Ridge_1    Eave_1  Wall_4    SurfaceInterior_4    ConvexEdge_7    GroundJunction_3  WindowCandidate_2
A building does not need every component to exist. Missing evidence must remain missing or explicitly inferred.
Stage 9 - Relation inference
Infer relations from measurable geometry:
incidence/intersection;
distance and adjacency;
normal angle;
containment;
shared boundaries;
vertical ordering;
topology of fitted components;
GIS contextual relationships.
Attach confidence and provenance to every relation.
Stage 10 - Confidence and provenance propagation
Each stage emits uncertainty. Do not average unrelated confidence numbers blindly.
For v0.2 use a transparent heuristic combination with logged inputs, then calibrate against synthetic ground truth. The code structure must permit learned calibration later.
Stage 11 - Write SIR
The final output is a valid Spatial IR document plus optional analysis sidecars. Raw dense point arrays should not bloat the main JSON; use URIs and hashes for sidecar data.
9. Airborne versus mobile sensing: do not pretend they observe the same world
The compiler must distinguish sensor regimes.
Airborne profile
Strengths:
terrainroof geometrybuilding footprints/massingcanopyroads and broad surface geometrylarge structures
Weaknesses:
vertical facadeswindows/doorsunder-canopy detailoccluded street furnitureinteriors
Airborne reconstruction should therefore infer missing walls or facade structure with lower confidence and explicit provenance.
Mobile / terrestrial profile
Strengths:
facadescurbsvehiclesstreet furnitureopeningstrunksstreet-level geometry
Weaknesses:
roof topsoccluded rear surfaceslarge-scale global consistency without SLAM/GNSS
Multimodal fusion
The long-term system can combine:
USGS/public airborne LiDARmobile LiDARGIS footprints and roadsaerial imagerystreet imagery where licensed/allowedBIM/CADSLAM trajectoriessatellite products
Spatial IR is the fusion boundary so missing evidence can be added later without rebuilding every downstream target manually.
10. Synthetic round-trip benchmark
This is the scientific backbone of the project.
10.1 Forward/inverse cycle
For a known scene S, forward sensor F, inverse model R, and target compiler C:
P = F(S)S_hat = R(P)P_hat = F(C(S_hat))
Evaluate both latent-world fidelity and measurement closure.
10.2 Required anti-cheating boundary
The inverse model may receive only declared observation inputs:
XYZ pointspublic sensor pose/trajectorypublic calibrationoptional intensity/return attributes if the track declares themoptional declared GIS/imagery side data
The inverse model may not receive:
hidden SIR entity IDsUSD prim pathsRTX stable object IDshidden material IDssimulator semantic labelshidden scene topology
Store hidden IDs in an evaluation-only namespace or separate file.

Preferred first backend:
NVIDIA Isaac Sim / Omniverse RTX LiDAR because it can provide exact scene correspondence for evaluation.

11. Theme, geometry, material, and asset compiler
Do not conflate theme with texture files.
A theme is a declarative rule set over semantics and context.
Example request:
entity.class = WallSurfaceentity.structural_role = convex_edgetheme = Cyberpunk_2080context = exterior / street-facing
Theme compiler result might request:
geometry_modifier = emissive_vertical_railmaterial_family = weathered_composite_panelemissive = trueasset_tags = [industrial, futuristic]
The material resolver can satisfy the request from multiple sources:
procedural shader/materialCC0/public-domain packuser-supplied asset packoffline AI-generated materialengine-native materialphotogrammetry-derived materialfallback canonical material
Every non-procedural asset should carry source, license, scale, and provenance metadata.
11.1 Theme file format
Use YAML or JSON. Example:
name: cyberpunk_demoversion: 0.1rules:  - match:      class: WallSurface      structural_role: convex_edge    emit:      geometry_modifier: emissive_rail      material:        family: composite_panel        tags: [dark, wet, futuristic]  - match:      class: Road      structural_role: curb_edge    emit:      material:        family: asphalt        tags: [wet]      geometry_modifier: luminous_lane_edge
11.2 Generated geometry must remain epistemically separate
If a Victorian theme adds quoins, trim, dormers, signs, or decorative assets, those entities must be marked generated, linked to the source entity, and never silently treated as measured reality.
Example:
Quoin_12  epistemic_state = generated  derived_from = WallCorner_4  provenance.algorithm = VictorianTheme.geometryGrammar
11.3 First theme demo
Implement only enough to prove separation:
Realistic default themeCyberpunk or Victorian demo theme
At minimum the theme must visibly change rules for two different semantic/structural contexts, not merely apply one global texture.
12. Target compilers
12.1 USD first
Keep OpenUSD as the first target because it supports hierarchy, metadata, relationships, simulation workflows, and the NVIDIA validation loop.
The USD compiler should:
preserve SIR IDs in custom metadata;
preserve semantic classes and epistemic state;
emit appropriate geometry representations;
optionally emit generated renderer proxies without altering canonical SIR;
maintain a map from SIR entity ID to target prim path for evaluation/debugging only.
12.2 glTF / Web target
Add a glTF export once USD works. glTF does not need to carry every SIR semantic field; export a metadata sidecar or use extensions where appropriate.
12.3 CityJSON / CityGML direction
Do not attempt full CityGML conformance in the first milestone. Add a mapping document and, if practical, a minimal CityJSON exporter for building/terrain entities.
12.4 3D Tiles / Cesium direction
Design tile IDs and metadata so future SIR entities can be streamed through 3D Tiles without changing identity. Do not build the full planetary runtime before the inverse compiler is validated.
13. World runtime and semantic LOD
This is a later milestone but the IR must not block it.
Traditional LOD reduces triangles. Semantic LOD can reduce world ontology:
100 km: city / terrain region10 km: building objects and major roads1 km: roof + walls + road segments100 m: windows, doors, trees, curbs10 m: trim, joints, signs, small generated detail
Runtime responsibilities eventually include:
geographic tilingout-of-core pagingsemantic LOD selectionmesh/asset instancingcoordinate rebasingcachingocclusionmaterial resolutionincremental updatescross-tile relation management
Do not implement a custom GPU runtime until existing engine targets expose a measured limitation that justifies it.

17. Engineering rules
1.  No hidden global state. Pass config and device explicitly.
2.  No hard-coded `.cuda()` calls in core code. Use device abstraction.
3.  Keep dense arrays out of JSON. Use NPZ/Parquet/PLY/LAZ sidecars with hashes and URIs.
4.  Use stable IDs. Deterministic IDs are preferred where reproducible matching is possible.
5.  Log every inference stage. A failed semantic graph must be debuggable back to evidence.
6.  Preserve the raw observation. Never overwrite source data.
7.  Schema migration is explicit. v0.1 documents must migrate to v0.2 rather than silently changing interpretation.
8.  Unit-test geometry. Plane fits, normal orientation, boundary tests, relation rules, coordinate transforms, and visibility logic need small synthetic tests.
9.  Integration-test the entire loop. A pipeline that only passes unit tests is insufficient.
10.  Avoid license contamination. Keep GPL tools as optional subprocess/plugin boundaries unless project licensing intentionally accepts GPL obligations.
11.  No renderer-specific semantics in the IR. Unreal/Unity/USD concepts belong in adapters.
12.  No theme-generated detail in reconstruction scores. Reconstruction and artistic materialization are separate tracks.

Treat GPL code carefully if the desired core is permissively licensed. It is acceptable to:

Do not copy GPL implementation code into a permissive core and relabel it.
Asset licensing is separate from code licensing. Theme packs must record source/license metadata. Procedural materials are the zero-dependency default.
19. Research questions the implementation must make testable
The project is strongest if it can falsify itself.
Build experiments that answer:
1.  Does a persistent semantic/topological IR improve reconstruction selection compared with a mesh-only baseline?
2.  Can forward LiDAR closure distinguish geometrically plausible but physically inconsistent reconstructions?
3.  Does explicit provenance prevent generated detail from contaminating measured-world analysis?
4.  Can semantic LOD reduce runtime cost more effectively than geometry-only LOD for large worlds?
5.  Does a hierarchical superpoint frontend reduce the cost of structural-role inference without losing critical boundaries?
6.  Can one reconstructed SIR be rematerialized into substantially different visual worlds without re-running perception?
7.  Can the same SIR drive rendering, collision/navigation, GIS queries, and sensor simulation without duplicating world identity?
8.  How does performance change with airborne versus mobile LiDAR density and observability?
9.  What value does topology add when geometry closure is already similar?
10.  Which confidence signals are actually calibrated enough to trust for inferred/unobserved surfaces?
Do not tune the benchmark solely to make the architecture look good.

22. Theme demo acceptance criteria
The theme system is proven only if:
1.  The original reconstructed SIR remains unchanged or is referenced immutably.
2.  A theme layer creates or selects material/geometry outputs based on semantic context.
3.  At least two structural roles behave differently.
4.  Generated entities carry generated provenance.
5.  Switching theme does not require reprocessing the raw LiDAR.
6.  The same entity IDs remain traceable across theme outputs.
Example demonstration:
WallSurface surface_interior  realistic -> brick/plaster PBR  cyberpunk -> dark composite panelWallSurface convex_edge  realistic -> masonry corner treatment  cyberpunk -> emissive rail geometryRoad curb_edge  realistic -> concrete curb  cyberpunk -> luminous curb strip
This proves that the system is not merely a global texture swap.

28. Final directive
Build the smallest real system that proves the architecture, not the largest demo that hides whether the architecture works.
The order of importance is:
1. reproducible observations2. correct geometry evidence3. stable semantic identity4. hierarchy and relations5. provenance and uncertainty6. physical closure7. theme/materialization8. scaling/runtime9. photorealism
A successful first release should let us point to one reconstructed entity and answer, programmatically:
What is it?What larger object is it part of?What geometry supports that conclusion?What is it adjacent to / connected to?Which observation(s) support it?Was it observed, inferred, imported, or generated?How confident are we?What alternative hypotheses existed?Can it be compiled to another engine or style without changing its identity?Can the compiled world reproduce the observations that caused us to infer it?
If the software can answer those questions, the Spatial World Compiler exists in a meaningful sense.
